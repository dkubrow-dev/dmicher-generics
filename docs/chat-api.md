# Чат и технические участники: API 1

`generics.chat` предоставляет доставку сообщений, учёт их идентификаторов, обработчики интерактивных элементов, отображение портретов и жизненный цикл технического пользователя с его Actor. Он не определяет смысл сообщения и не исполняет игровые команды из его содержимого.

Конкретный потребитель — Spotlight: ему принадлежат заявки, опросы, таймеры, тексты уведомлений, адресаты и настройки отображения. В Generics перенесены повторяемые механизмы. Для реплики существующего НПС нужен обычный `Actor` в `speaker`; технический пользователь для этого не создаётся.

## Подключение и ответственность

```js
import { requireApiVersion } from "../../dmicher-generics/scripts/api.js";
const generics = requireApiVersion(1);
const { chat } = generics;
const ownerId = "dmicher-example";
```

В примерах `dmicher-example` означает ID собственного установленного модуля. Потребитель объявляет зависимость от Generics, но не от Spotlight или Premium. Загрузка API сама не создаёт пользователей, сообщения или настройки. Потребитель явно создаёт сервис и подключает нужные обработчики.

| Generics | Модуль-потребитель |
| --- | --- |
| Доставка, приватные копии, локальная очередь | Когда, кому и зачем отправлять сообщение |
| Метки владельца, канала и ключа | ID заявки, опроса, события и их предметное состояние |
| Привязка кнопок и форм к актуальному документу | Текст, разметка, доступные действия и проверка их допустимости |
| Создание и восстановление общего Информатора, имя, изображение, локализация, хранение ID | Включение и оформление собственных сообщений |
| Отображение выбранного портрета и fallback | Выбор портрета и предпочтения отображения |

Создавайте один долгоживущий `createMessageService` на сочетание `ownerId` и `channel`; для общего Информатора — через `chat.informer.createMessageService`. Новый сервис сообщений перед каждым вызовом теряет общую локальную очередь доставки. Создание и ремонт личности имеют отдельную общую очередь внутри текущего клиента мира. Разные клиенты общей блокировки не получают; запись выполняет избранный полный ГМ.

## Адресаты и автор

`create(data, options)` всегда требует явного `options.audience`. Поле `data.whisper` не заменяет этот выбор. По умолчанию отправляется один документ (`delivery: "shared"`); `delivery: "per-recipient"` создаёт отдельный whisper на каждого адресата.

| `audience` | Результат |
| --- | --- |
| `{ type: "public" }` | Публичный документ с `whisper: []`; только `shared` |
| `{ type: "users", userIds: [id1, id2] }` | Указанные существующие пользователи без повторов |
| `{ type: "gms" }` | Мастера и помощники: роль 3 или 4 |
| `{ type: "players" }` | Игроки и доверенные игроки: роль 1 или 2 |
| `{ type: "all" }` | Все существующие пользователи, включая отсутствующих в сети |

Из непубличных адресатов по умолчанию исключаются пользователи с общей меткой технической личности. Для миграции потребитель может передать `excludeUser(user)`. Пустой список приватных адресатов, включая список из одних удалённых пользователей, означает **никому**, возвращается `[]`. Он никогда не превращается в публичное сообщение. `public` и `all` имеют разные значения.

Автор и адресат — разные роли Foundry. Без явного `author` используется текущий пользователь; другой автор разрешён только мастеру/помощнику, а Foundry дополнительно проверяет создание документа. Автор обычно видит свой whisper даже без своего ID в адресатах. Поэтому сообщение игрокам от текущего ГМ не обещает скрыть его от этого ГМ. Для независимых персональных копий Spotlight использует технического пользователя как автора.

`blind` не является универсальным способом скрывать обычные текстовые сообщения: в Foundry 13 проверка скрытого содержимого зависит от наличия броска, а в 14 правила изменены. Общая привязка действий проверяет оба фактических свойства документа — `visible === true` и `isContentVisible === true`. Не воспроизводите эти правила по одному массиву `whisper`. Право ГМ изменять документ также не означает, что Foundry показывает ему содержимое каждого whisper.

`resolveChatAudience(audience, { excludeUser })` позволяет отдельно получить `{ public, recipients }`. Это снимок текущего состава пользователей, а не подписка на будущие подключения. Перед записью после асинхронной подготовки сервис повторно проверяет существование адресатов и их соответствие выбранной аудитории. Потеря нужной роли останавливает отправку с ошибкой; уже опубликованные сообщения автоматически не отзываются при будущих изменениях ролей.

## Реплика существующего НПС

```js
const speech = chat.createMessageService({ ownerId, channel: "speech" });

async function sayAsNpc(actorId, text) {
  if (!game.user.isGM) throw new Error("Требуются права мастера");
  const actor = game.actors.get(actorId);
  if (!actor) throw new Error("НПС не найден");
  return speech.create({
    author: game.user.id,
    speaker: chat.buildChatSpeaker({ actor: actor.id, alias: actor.name }),
    content: `<p>${generics.utilities.escapeHTML(text)}</p>`
  }, {
    audience: { type: "public" }, kind: "npc-speech", technical: false
  });
}
```

НПС не получает техническую метку, его права и пользователь не изменяются. `buildChatSpeaker` принимает явные `actor`, `token`, `scene` и `alias`; ID можно передать строкой или документом. Неуказанные ссылки становятся `null`. Утилита не берёт случайный управляемый токен ГМ. Предметную допустимость выбранного НПС проверяет вызывающий модуль.

Сервис принимает подготовленные данные ChatMessage и сохраняет частные flags. Его собственные `whisper` и `flags["dmicher-generics"].chat` имеют приоритет. `create` возвращает массив документов даже при одном публичном сообщении. HTML и разрешённые источники медиа выбирает потребитель; для простого текста используйте `escapeHTML`.

## Общий Информатор

`generics.chat.informer` — единая техническая личность семейства. Её жизненным циклом владеет только Generics: при загрузке избранный полный ГМ создаёт собственные User и Actor, если их ещё нет. Actor находится в собственной папке `dmicher modules/generic`; прежние документы Spotlight не присваиваются, не мигрируются и не удаляются.

Потребитель не регистрирует настройку личности и не вызывает её создание, включение или удаление. `informer.get()` только читает `{ user, actor, folder }`, а `informer.portrait` содержит путь общего изображения. Имя переименованного собственного пользователя сохраняется, Actor скрыт от игроков, пользователь не получает права ГМ. Перед каждой отправкой Generics проверяет и при необходимости восстанавливает свои документы. Настройка приветствия не управляет их доступностью.

```js
const notices = generics.chat.informer.createMessageService({ ownerId, channel: "notices" });
await notices.create({ content: "<p>Проверка подготовки завершена</p>" }, {
  audience: { type: "gms" }, key: "prep-check-001", kind: "notice"
});
await notices.create({ content: "<p>Перерыв окончен</p>" }, {
  audience: { type: "players" }, delivery: "per-recipient",
  key: "break-finished-001", kind: "break-finished",
  enabled: () => game.settings.get(ownerId, "chatEnabled")
});
```

Возвращается стандартный сервис с `create/find/get/update/remove/removeAll`. Общий автор, speaker и признак технического сообщения задаются Generics и не подменяются данными потребителя. Содержимое, категория, явная аудитория, предметные flags, ключи повторов и `enabled()` принадлежат потребителю. Пустая приватная аудитория остаётся пустой. Публикация от Информатора требует мастера или помощника; создание личности выполняет избранный полный мастер. Без подключённого полного мастера помощник может использовать уже существующую пару, но не создавать отсутствующие документы.

Если `data` — функция, она получает `{key, recipientId, informer: {user, actor, folder, portrait}}`. Это позволяет потребителю сохранить предметный снимок отображения, не управляя жизненным циклом. Отключение одной категории сообщений не удаляет Информатора и не влияет на другие модули. Старая низкоуровневая фабрика `createManagedIdentity` сохранена ради совместимости API; новые потребители общего Информатора используют только `chat.informer`.


## Идентификаторы, повторы и управление

Каждый новый документ получает метку:

```js
{
  apiVersion: 1,
  ownerId: "dmicher-example",
  channel: "notices",
  key: "prep-check-001",
  kind: "notice",
  technical: true,
  recipientId: "user-id" // null для shared
}
```

Это `flags["dmicher-generics"].chat`. `getChatMetadata(message)` возвращает метку версии 1 или `null`; `isTechnicalMessage(message)` требует именно `technical === true`. Обычная реплика НПС не становится техническим событием только потому, что отправлена через Generics.

Без заданного ключа каждый вызов получает новый случайный ключ. С заданным ключом сервис повторно использует существующие копии своего владельца и канала. Изменение `kind`, `technical` или режима `shared`/`per-recipient` при том же ключе отклоняется. Для `shared` изменение адресатов также отклоняется. Повтор `per-recipient` может дополнить недостающих адресатов: он не удаляет уже отправленные копии и не переписывает их текст. Для нового события или иного содержимого используйте новый ключ либо явное `update`.

```js
const copies = notices.find({ key: "prep-check-001" });
const one = copies[0] && notices.get(copies[0].id);
if (one) {
  await notices.update(one.id, {
    content: "<p>Проверка подготовки завершена повторно</p>",
    moduleFlags: { preparation: { reviewed: true } }
  });
  await notices.remove(one.id);
}
const cleanup = await notices.removeAll({ key: "prep-check-001" });
if (cleanup.failed.length) {
  console.error("Не все сообщения удалены", cleanup.failed.map(({ documentId, error }) => ({ documentId, error })));
}
```

`find` принимает необязательные фильтры `key`, `kind`, `recipientId`, `documentIds`. `get(id)` возвращает только документ своего сервиса или `null`. Поиск выполняется по известным этому клиенту `game.messages`, а не по серверному архиву, и не фильтрует записи по отображаемости: ГМ может обслуживать приватные копии, которых нет в его видимом чате.

`update` принимает только `content` и `moduleFlags`; последние передаются в `flags[ownerId]` по обычным правилам обновления Foundry. Автор, адресаты и общая метка учёта этим методом не меняются. Перед `update`/`remove` сервис повторно находит документ своего владельца и требует `canUserModify(game.user, operation) === true`. Отсутствие документа или права — ошибка. `removeAll` продолжает после отдельных ошибок и возвращает `{ removed: [id], failed: [{ documentId, error }] }`.

Если создание одной копии завершается ошибкой, сервис пытается удалить только копии, созданные этим вызовом. Найденные прежние копии остаются. При неудачном удалении выбрасывается ошибка с исходной `cause` и `rollbackFailures: [{ documentId, cause }]`; диагностический callback `onRollbackError(error, message)` задаётся при создании сервиса. Это компенсация с возможным остатком, а не транзакция.

Очередь и подавление повторов локальны одному сервису в одном клиенте. Потеря ответа после записи, конкурирующие ГМ и повтор после удаления истории требуют собственного решения потребителя. Сервис не обещает выполнение ровно один раз и не переигрывает автоматически внешние действия.

## Кнопки, формы и актуальные права

Кнопка содержит только ID и подпись. Обработчик остаётся в коде модуля:

```js
const hookId = Hooks.on(chat.getChatMessageRenderHook(), (message, html) => {
  if (!notices.get(message.id) || chat.getChatMetadata(message)?.kind !== "note-link") return;
  chat.bindActions({
    moduleId: ownerId, message, root: html, key: "note-link",
    actions: [{
      selector: '[data-dmicher-chat-action="open-note"]',
      authorize: ({ message: current, user }) => {
        const note = game.journal.get(current.getFlag(ownerId, "noteId"));
        return Boolean(user.isGM && note?.testUserPermission(user, "OBSERVER"));
      },
      handle: ({ message: current, user }) => {
        const note = game.journal.get(current.getFlag(ownerId, "noteId"));
        if (!user.isGM || !note?.testUserPermission(user, "OBSERVER")) return;
        return note.sheet.render({ force: true });
      }
    }],
    onError: (error) => ui.notifications.error(error.message)
  });
});

async function postNoteCard(noteId, key) {
  if (!game.user.isGM || !game.journal.get(noteId)) throw new Error("Заметка недоступна");
  const content = `<p>Открыть заметку</p>${chat.renderActionButton({ id: "open-note", label: "Открыть" })}`;
  return notices.create({
    content,
    flags: { [ownerId]: { noteId } }
  }, { audience: { type: "gms" }, key, kind: "note-link" });
}
// При демонтаже потребителя: Hooks.off(chat.getChatMessageRenderHook(), hookId).
```

Пример использует существующий JournalEntry, его ID и ключ события задаёт потребитель при вызове `postNoteCard`. Hook регистрируется до создания карточек. Правило доступа к заметке принадлежит модулю и проверяется непосредственно перед действием.

Каждое действие требует `selector`, `authorize(context)` и `handle(context)`; `event` по умолчанию `click`, для формы укажите `submit`. Контекст содержит актуальные `message`, `user`, событие `event`, найденный `control` (синоним `element`) и корень `root`. При делегировании формы данные читайте из `control`, а не из `event.currentTarget`.

`authorize` должен вернуть строго `true`; Promise допустим. После ожидания заново проверяются существование и видимость документа, тот же пользователь/роль, ревизия документа и принадлежность элемента корню. Синхронные проверки и локальные действия выполняются синхронно. Удалённая карточка или скрытое содержимое не исполняются.

Повторная привязка того же `moduleId + key + root` снимает прежние обработчики и инвалидирует ожидающую авторизацию. Другие привязки сохраняются. Пока Promise обработчика не завершён, повторное действие **на том же элементе этой привязки** не запускается. Это не глобальная блокировка процесса и не защита от повторного действия в другом окне/клиенте. Возвращайте Promise действия, если нужно учитывать его ожидание.

`bindActions` возвращает идемпотентный disposer. Сохраните его, если снимаете функцию без перерендера/удаления её DOM. Отписка от hook и снятие уже созданных привязок — разные операции. Disposer предотвращает ещё не начавшийся handler, но не отменяет запись или другое действие, уже начатое handler. После собственных `await` предметный обработчик сам повторно проверяет актуальные условия.

ID, flags и локальные callbacks не являются доказательством сетевой авторизации. Generics не использует `eval`, не загружает обработчики из flags и не предоставляет универсальную сокет-команду для выполнения кнопки от имени ГМ. Предметные сетевые обработчики должны проверять собственное состояние и права независимо от наличия кнопки.

## Портреты и совместимость

```js
const releasePortrait = chat.renderChatPortrait(html, {
  moduleId: ownerId,
  sources: [savedPortrait, fallbackPortrait, "icons/svg/mystery-man.svg"],
  alt: speakerName
});
// Если нужно прекратить этот renderer до следующего render:
releasePortrait();
```

Потребитель задаёт упорядоченные источники, подпись и при необходимости `selector`. По умолчанию обрабатывается `.message-sender .avatar img, .message-sender .avatar video`. Видео воспроизводится без звука, при ошибках используется конечная цепочка fallback; устаревший обработчик ошибки не заменяет новый портрет. Повторный render с теми же источниками сохраняет уже выбранный fallback. Отсутствующий портрет DOM — допустимый no-op. Один модуль не присваивает слот портрета другого без освобождения прежнего владельца.

Выбор изображения по flags заявки, интеграция `ChatPortraitReplaceData` и частная локализация остаются в Spotlight. Общий renderer не знает этих flags.

`getChatMessageClass`, `getChatMessageRenderHook`, `buildChatSpeaker`, `getMessageAuthorId`, `getMessageAuthorName`, `applyChatMessageMode` объединяют используемые различия Foundry. Последняя функция применяет штатный текущий режим чата/бросков к переданным данным. При последующей отправке через сервис всё равно задайте соответствующий явный `audience`: сервис не читает режим как разрешение самостоятельно расширить адресатов.

## Миграция Spotlight и старой истории


Для сообщений `readLegacyMetadata(message)` возвращает прежнюю метку только распознанных документов своего канала или `null`. Он нужен для поиска и повторной доставки по историческому ключу без массовой перезаписи чата. Не возвращайте произвольные flags другого модуля. Общая метка нового владельца имеет приоритет над legacy-адаптером.

Новые технические сообщения Spotlight сохраняют его прежний `FLAGS.technical` с `key`, `recipientId`, автором и снимком портрета, добавляя общую метку Generics. Частные flags заявок, результатов опросов и таймеров остаются у Spotlight. Старое поведение пустого `whisper` как «все люди, отдельными копиями» преобразуется только его адаптером в `{ type: "all" }`; общий API пустой приватный список не расширяет.

Эти метки обеспечивают совместимость и учёт, но не делают данные доверенными. Источниками предметной истины остаются собственное состояние модуля и проверки прав Foundry.
